## 一、功能完整度评估

### 1.1 功能覆盖地图

将平台功能按「创作—阅读—互动—管理」四大领域进行覆盖度分析：

| 功能领域 | 已实现 | 部分实现 | 缺失 | 覆盖度 |
|---------|--------|----------|------|--------|
| **创作** | 故事创建、章节编辑、分支创建、番外创建、角色管理 | 协作编辑（Schema 存在但 UI 未完整）、合并申请（Modal 存在但流程待验证） | 草稿自动保存、版本历史、离线编辑、AI 辅助写作（Service 存在但路由空壳） | 60% |
| **阅读** | Markdown 渲染、设置面板（字号/主题/字体）、阅读历史、存档点、评论、阅读路径 | 搜索（仅前端过滤无后端 API）、继续阅读 | 全文搜索、阅读进度同步、离线阅读、TTS 朗读、沉浸模式 | 55% |
| **互动** | 点赞、半星评分+理由标签、分享、评论 | 通知系统（铃铛图标存在但无真实通知）、书单收藏 | 关注作者、@提及、私信、互动消息流、打赏 | 45% |
| **管理** | CMS 配置、RBAC 权限、内容审核（自动+人工）、编辑改稿、角色管理 | 收益结算（前后端存在但有 bug）、数据看板 | 运营数据导出、用户管理后台、内容推荐引擎、SEO 管理 | 50% |
| **发现** | 首页轮播/频道/金榜/编辑推荐/书单/继续阅读/热门书单、宇宙发现页、推荐页、新书页 | 排行榜（仅按 viewCount 排序无综合算法） | 个性化推荐、标签聚合页、专题运营、热门话题 | 55% |

**整体覆盖度: ~53%** — 核心骨架已搭建完成，但大量"最后一公里"功能处于半成品或空壳状态。

## 二、需求优先级矩阵

按「用户影响 × 实现紧急度」四象限排列：

### 象限 I — 高影响 + 高紧急（必须做）

| 优先级 | 需求 | 用户价值 | 工程评估 | 依赖 |
|--------|------|---------|---------|------|
| **P0-1** | 全文搜索 API + 搜索结果页 | 读者找到内容的唯一入口 | 中（SQLite FTS5 / 切 PostgreSQL 后用 pg_search） | 无 |
| **P0-2** | 通知系统（评论回复、分支被创建、合流请求） | 用户粘性核心驱动 | 高（需 WebSocket 推送 + 通知表 + 前端消费） | G2 |
| **P0-3** | 草稿自动保存 | 创作者体验的底线 | 低（TipTap onChange + debounce + API） | 无 |
| **P0-4** | 安全修复（JWT/CORS/Socket.IO 认证） | 平台存活前提 | 低（纯后端配置修复） | 无 |

### 象限 II — 高影响 + 低紧急（应该做）

| 优先级 | 需求 | 用户价值 | 工程评估 |
|--------|------|---------|---------|
| **P1-1** | 关注系统 + 作者动态流 | 社区活跃度 | 中（新增 Follow 模型 + 动态 feed） |
| **P1-2** | 个性化推荐算法 | 内容分发效率 | 高（需行为数据积累 + 算法选型） |
| **P1-3** | 阅读路径完整闭环 | 平行宇宙核心差异化 | 中（已有基础，补全流程） |
| **P1-4** | 分支合流完整流程 | 创作者协作核心 | 中（合并申请 Modal 已有，需完整审批流） |
| **P1-5** | 代码分割 + 首屏优化 | 首次访问体验 | 低（React.lazy + Vite manualChunks） |

### 象限 III — 低影响 + 高紧急（快做快收）

| 优先级 | 需求 | 说明 |
|--------|------|------|
| **P2-1** | 404 页面 | 5 分钟搞定，当前空白页 |
| **P2-2** | Toast 替换残余 alert() | CODE_REVIEW 中已标记但未全部替换 |
| **P2-3** | 收益结算 bug 修复 | 已在审查报告中标记 |

### 象限 IV — 低影响 + 低紧急（停车场）

| 需求 | 备注 |
|------|------|
| AI 辅助写作 | 保留 Service 壳，等 AI 合作方确定后接入 |
| 区块链存证 | 暂无业务场景 |
| PWA/离线阅读 | 等移动端用户量达到阈值后启动 |
| TTS 朗读 | 等核心体验稳定后作为增值功能 |
| 多语言 | 等海外拓展需求明确 |

## 三、核心用户故事

### US-1: 读者从分支树探索新故事线
**作为** 一名读者，
**我想** 在阅读到某个章节时，看到该章节分叉出的所有平行分支，
**以便** 选择我感兴趣的故事走向继续阅读。

**验收标准**:
- Given 我在阅读第 N 章, When 该章节存在分支, Then 页面底部/侧边显示分支入口卡片
- Given 我点击分支树中某个分支节点, When 分支有内容, Then 直接跳转到该分支的第一章
- Given 分支树有 3+ 层嵌套, When 我缩放/拖拽树图, Then ReactFlow 流畅交互不卡顿

### US-2: 创作者从任意章节发起分支
**作为** 一名读者/创作者，
**我想** 在阅读到某个章节时创建一个平行分支，
**以便** 探索"如果当时选了另一条路会怎样"。

**验收标准**:
- Given 我已登录且在阅读某章节, When 我点击"创建分支", Then 弹出分支创建表单（标题、简介、类型）
- Given 分支创建成功, When 返回原故事页, Then 分支树中新增该分支节点
- Given 分支作者不是原故事作者, When 分支发布, Then 原作者收到通知

### US-3: 读者通过书单发现内容
**作为** 一名新读者，
**我想** 浏览精选书单来找到适合我的阅读路径，
**以便** 快速进入平行宇宙的阅读体验。

**验收标准**:
- Given 我在书单页, When 浏览书单列表, Then 每个书单显示封面、标题、作品数、导游评分
- Given 我进入某个书单, When 按顺序阅读, Then 进度条实时更新，已完成章节打勾
- Given 我读完书单所有内容, When 返回书单页, Then 显示"已完成"徽章

### US-4: 创作者使用编辑器协作写作
**作为** 一名合著者，
**我想** 与原作者在同一故事下协作编辑章节，
**以便** 共同完成一个大型故事项目。

**验收标准**:
- Given 原作者邀请我为合著者, When 我接受邀请, Then 我获得指定章节的编辑权限
- Given 我正在编辑某章节, When 另一人也尝试编辑, Then 显示"正在被 XX 编辑"的锁定提示
- Given 我保存编辑内容, When 协作者刷新, Then 看到最新内容

### US-5: 作者通过收益系统获得回报
**作为** 一名创作者，
**我想** 查看我的故事/分支/番外带来的收益明细，
**以便** 了解哪些内容最受欢迎并持续创作。

**验收标准**:
- Given 我有已发布的内容, When 进入收益中心, Then 看到总余额和各作品收益明细
- Given 某条分支引用了我的主线角色, When 产生收益, Then 按设定分成比例自动分配
- Given 我的余额达到提现门槛, When 我申请提现, Then 提交提现请求

### US-6: 管理员审核争议内容
**作为** 一名内容审核员，
**我想** 在审核后台查看被标记的内容并做出处置决定，
**以便** 维护社区内容质量。

**验收标准**:
- Given 有新审核工单, When 我进入审核后台, Then 看到待处理列表（按严重程度排序）
- Given 我打开某个工单, When 查看内容快照和 AI 审核标签, Then 可以通过/驳回/升级
- Given 我做出驳回决定, When 作者申诉, Then 生成复审工单

### US-7: 读者搜索特定故事或作者
**作为** 一名读者，
**我想** 通过关键词搜索故事标题、简介、作者名，
**以便** 快速找到我想读的内容。

**验收标准**:
- Given 我在搜索框输入关键词, When 提交搜索, Then 500ms 内返回匹配结果
- Given 搜索有结果, When 展示结果列表, Then 按相关度排序，显示标题/作者/匹配片段
- Given 搜索无结果, When 展示空状态, Then 提供推荐热门内容作为替代

### US-8: 创作者申请分支合流到主线
**作为** 一名分支创作者，
**我想** 将我的高质量分支合流回原作者的主线，
**以便** 让我的创作成为官方正史的一部分。

**验收标准**:
- Given 我的分支已完结, When 我提交合流申请, Then 原作者收到申请通知
- Given 原作者查看申请, When 同意合流, Then 分支章节合并到主线对应位置
- Given 合流完成, When 读者浏览, Then 分支树显示合流标记

## 四、功能风险清单

### 4.1 已实现功能的设计缺陷

| 风险ID | 功能 | 风险描述 | 严重性 | 影响 |
|--------|------|---------|--------|------|
| R1 | **分支树可视化** | ReactFlow 在分支数量 >50 时性能急剧下降；节点定位用固定步长（`CHAPTER_X_STEP=280`），深分支会溢出画布 | 🔴 HIGH | 大型故事树不可用 |
| R2 | **评分系统** | 半星评分存储为 `valueInt`（整数），前端换算逻辑分散，可能出现 0.5 精度丢失 | 🟠 MEDIUM | 评分显示不一致 |
| R3 | **协作编辑** | Socket.IO 无认证 + 编辑锁基于客户端传来的 userId，可被恶意冒用 | 🔴 HIGH | 任意用户可锁定/解锁他人章节 |
| R4 | **书单系统** | 书单 item 只关联 Chapter 而非 Story，无法整本收藏 | 🟠 MEDIUM | 书单只能收藏零散章节而非完整故事 |
| R5 | **收益结算** | Revenue Service 无认证（P2-8），任何人可触发结算；`distributeCurationRewards` 存在 N+1 查询 | 🔴 HIGH | 收益数据可被篡改 |
| R6 | **阅读历史** | `ReadingHistory` 以 `(userId, chapterId)` 为唯一约束，同一章节只能记录最后一次阅读，无法记录重复阅读行为 | 🟡 LOW | 丢失用户行为数据 |
| R7 | **JSON 存字符串** | 8 个字段用 String 存 JSON（SQLite 限制），无结构校验，解析失败时静默吞错 | 🟠 MEDIUM | 数据完整性无保障 |
| R8 | **首页数据加载** | 4 个并行 API 请求全部在 `useEffect` 中发起，无 React Query 缓存，每次进入首页都重新加载 | 🟠 MEDIUM | 性能浪费+闪烁 |
| R9 | **评论系统** | 评论仅支持章节级，无故事级/分支级评论，无回复/嵌套 | 🟡 LOW | 互动深度不足 |
| R10 | **角色系统** | Character 模型存在但 `attributes` 用 JSON 字符串，前端角色管理页功能单薄 | 🟡 LOW | 角色系统形同虚设 |

### 4.2 用户体验问题

| 风险ID | 问题描述 |
|--------|---------|
| UX1 | 搜索框仅前端过滤已有 stories 列表，无法搜索分支/番外/书单，体验为假搜索 |
| UX2 | 侧边栏需要鼠标悬停才展开，新用户不知道侧边栏存在，功能发现性差 |
| UX3 | 分支创建后无引导跳转到编辑器，用户需手动导航 |
| UX4 | 阅读页无章节间快速跳转（上一章/下一章按钮虽存在但无键盘快捷键） |
| UX5 | 评分弹窗的半星交互不直觉（代码审查已修复显示但交互仍有摩擦） |
| UX6 | 手机端导航栏 5 个 Tab 信息密度过高，图标+文字在小屏上挤压 |
| UX7 | 无 404 页面，未知路由显示空白 |

## 六、下一迭代建议（Sprint 1-2）

> 建议按「安全止血 → 核心补齐 → 体验打磨」节奏推进，每个功能含验收标准概述。

### 建议 1: 安全修复包（Sprint 1, 预计 3 天）

**内容**: 修复 CODE_REVIEW_REPORT 中所有 P0 安全问题
- JWT 硬编码密钥 → 启动时强制检查
- CORS `origin: true` → 限制到已知域名
- Socket.IO 添加 JWT 握手认证
- Revenue 结算 API 添加 authenticate 中间件
- 数据库错误信息不再泄露给客户端

**验收标准**:
- [ ] JWT_SECRET 缺失时服务拒绝启动
- [ ] 非 whitelist 域名的跨域请求被拒绝
- [ ] WebSocket 连接无有效 token 时断开
- [ ] `/api/revenue/settle/*` 未认证返回 401
- [ ] 生产环境 500 错误不包含 SQL/表名信息

### 建议 2: 全文搜索（Sprint 1-2, 预计 5 天）

**内容**:
- 后端: 搜索 API（支持标题/简介/作者模糊匹配，优先用 SQLite FTS5）
- 前端: 搜索结果页（综合结果 + 分类 Tab: 故事/分支/番外/作者）
- 搜索框接入: MainLayout 中提交搜索 → 跳转搜索结果页

**验收标准**:
- Given 输入关键词, When 提交搜索, Then 500ms 内返回结果
- Given 结果 >20 条, When 滚动到底部, Then 自动加载下一页
- Given 无匹配, When 展示空状态, Then 显示热门推荐

### 建议 3: 草稿自动保存（Sprint 1, 预计 2 天）

**内容**:
- TipTap 编辑器 onChange → debounce 3s → 调用章节更新 API
- 保存状态指示器（已保存/保存中/保存失败）
- 离开页面时未保存提醒（beforeunload）

**验收标准**:
- Given 编辑内容后 3 秒无操作, When 自动保存触发, Then 状态指示器显示"已保存"
- Given 保存失败, When 指示器显示错误, Then 提供重试按钮
- Given 有未保存内容, When 用户尝试关闭标签, Then 弹出确认提示

### 建议 4: 通知系统 v1（Sprint 2, 预计 5 天）

**内容**:
- 数据模型: Notification 表（userId, type, title, content, isRead, relatedId, createdAt）
- 通知类型: 分支创建通知（原作者收到）、评论回复通知、合流请求通知
- API: GET /notifications（分页）+ PATCH /notifications/:id/read + GET /notifications/unread-count
- 前端: 铃铛图标显示未读数 badge → 点击展开通知列表浮层

**验收标准**:
- Given 有人在我的故事下创建分支, When 我刷新页面, Then 铃铛显示未读数 +1
