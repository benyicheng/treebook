# 功能审计（现状 → 缺失能力 → 风险）

## 现有能力（已具备的稳定链路）

- 内容写入侧：Story/Chapter/Comment/Spinoff/Booklist 等控制器写入成功后旁路入队机审（不阻塞）
- 机审侧：moderation_jobs（队列）+ worker 消费 + moderation_decisions（决策落库）
- 生效侧：读取详情接口在 enforce 模式下根据最新决策进行遮罩（rejected 时屏蔽文本）
- RBAC：具备角色/权限表与权限校验中间件（JWT 中扁平 permissions）
- 存储：存在本地 uploads 目录的最小化落盘能力

## 缺失能力与缺口

### 1) 管理员人工审核流程（多级工作流）

- 缺少“待处理队列/工单系统”：机审拒绝或失败后无法形成可追踪的处置单
- 缺少“预览/批注/退回修改/通过/拒绝”的统一处置台与完整审核日志（可审计、可回溯）
- 缺少多级复核编排：如 L1 初审 → L2 复审 → 终审（并行/串行）与 SLA

### 2) 编辑人工干预机制

- 当前仅 author/admin 能修改内容；缺少“编辑”角色对内容发布前的校对干预路径
- 缺少编辑操作留痕（至少 180 天）、以及与审核/发布状态的协同

### 3) 编辑器媒体上传

- 用户侧缺少上传 API 与前端上传/预览链路（现多依赖外部 URL）
- 缺少媒体资产表：无法记录 owner、mime、size、hash、状态、风险日志、引用关系与生命周期
- 缺少安全策略：大小限制、基础病毒扫描、失败留痕、异常降级开关

## 风险点（当前体系的边界）

- 媒体机审目前仅做 URL 域名可信度校验，无法覆盖真实图片/音视频内容识别
- 内容字段级审核与对象级遮罩粒度存在差异（当前更多为整体遮罩）
